# 0077. ディスクのイメージの大きさに比例する費用を外す

## Status

Accepted（2026-10-05に運用者が設計を承認し、同じ日に実装した）。

## Date

2026-10-05

## Context

- Linux向けの実行ファイル（数MiB）を置くために、ディスクのイメージを2MiBから32MiBへ上げた。全検査が、479項目のうち10項目の時間切れで落ちた。起動が、1回あたり約9秒延びていた。
- 区間ごとに測って、原因を分けた（`docs/verification-coverage.md`の「ディスクのイメージの読み書きの所要」）。延びていたのは5つの区間で、どれもイメージの大きさ（か、使っている量）に比例していた。
  - ブートローダが、ESPのイメージを読んでRAMに置く（32MiBで約3.6秒）。装置（virtio-blk）が在る回は、カーネルはそのイメージを使わない。
  - 起動時に、装置からイメージを読む（約0.6秒）と、装置へ書き戻す（約2.8秒）。4KiBずつの要求で、32MiBなら8,192回になる。費用は、バイト数ではなく要求の回数に付いていた。
  - イメージの全体の検査値を計算する（約2.5秒）。
  - 壊したイメージの検査が、使っている量の全体を、壊し方ごとにコピーし直す（約0.3秒）。
- イメージの全体を読む・書く形は、`ADR-0034`の決定である。ext2の実装が、イメージの全体のバイト列を借りる形で書かれている。同じADRが、見直すきっかけを「イメージがRAMに載らない大きさになったとき、または部分読みが実測で要る場面が出たとき」としていた。
- イメージの全体をRAMに置くことをやめる（ブロックのキャッシュと、変わったブロックだけを書く形）のは、ext2の読む側と書く側の作り直しになる。ここでは扱わない。

## Decision

イメージの全体をRAMに置く形（`ADR-0034`）は、そのままにする。その上で、イメージの大きさに比例していた費用を、1つずつ外す。

### 1. 区間ごとの所要を、起動ログに出す

ブートローダが1行、カーネルが2行、`fs-timing:`の行にサイクル数を出す。値は実行ごとに揺れるので、判定には載せない。直しの前後と、イメージの大きさを変えたときを、同じ行で比べるための行である。

### 2. 起動時の読み書きは、1MiBまでの要求にまとめる

- 1回の要求の上限は、装置が申告するセグメントの上限（`VIRTIO_BLK_F_SIZE_MAX`の`size_max`）と、こちらで決めた上限（1MiB）の、小さいほうにする。データは1つのセグメント（物理的に連続した範囲）で渡すので、要求の上限はセグメントの上限である。
- **装置が上限を申告していなければ、装置の側の上限は無いものとして扱う。** virtioの仕様では、この機能を申告しない装置は、セグメントの大きさを制限しない。こちらの上限だけが効く。QEMUのvirtio-blkは、`size_max`を申告しない（`seg_max`だけを申告する。実測で254）。
- 受けると答えていない機能でも、申告された上限には従う。`seg_max`が申告されていて0なら、装置を使わずに止まる。
- こちらの上限を1MiBにしたのは、起動時の要求を、割り込みを禁じたままポーリングで待つためである。1回の待ちは約1ミリ秒だった（実測）。
- 実行時の保存は、イメージの全体を1回の要求で出す形のままである。装置が上限を申告していて、イメージの全体がそれを越えるときは、要求を出さずに保存の失敗として返す。

### 3. 装置から起動する回は、ESPにイメージを置かない

- 検査の道具が、virtio-blkを付けてディレクトリから起動する回には、ESPへイメージを置かない。ブートローダは「イメージが無い。カーネルは装置を使う」と1行出して進む（この道は、以前から在る）。
- 起動媒体のイメージ（VirtualBoxと実機に渡すもの）と、virtio-blkを付けない変種には、今までどおり置く。「起動媒体1つで、装置の在る・無しのどちらでも起動する」（`ADR-0068`）は、起動媒体の側で保つ。
- ブートローダは変えていない。

### 4. 検査値は、管理用の部分だけを覆う。イメージの全体の検査値は、ボリュームの名前の欄に書く

- 起動時にカーネルが計算する検査値の範囲を、イメージの全体から、**管理用の部分**へ絞る。先頭から、グループ0のinodeの表の終わりまでである（スーパーブロック、グループの記述子、ビットマップ、inodeの表）。大きさは、イメージの大きさやファイルの中身の量に依らず、inodeの数で決まる。
- ホストの検査は、同じ範囲を、イメージのファイルから計算して突き合わせる。範囲の決め方は`common`のext2に1つだけ置き、カーネルとホストの両方が使う。
- **管理用の部分だけでは、ファイルの中身だけが違う古いイメージを見分けられない**（大きさが同じなら、管理用の部分は変わらない。時刻は、ビルドのときに潰してある）。そこで、**ビルドのときに、イメージの全体の検査値を、スーパーブロックのボリュームの名前の欄（`s_volume_name`）へ文字で書く**（`zeikos-`に16進8桁を続けた15文字）。この欄は管理用の部分に入るので、中身が1バイトでも違うイメージは、管理用の部分の検査値も違う値になる。
- RAMのイメージから起動した回は、今までどおり、ビルドしたときの値と比べる。比べる値が、管理用の部分の検査値になった。
- **イメージの全体のバイト一致は、イメージを取り出す検査が持つ**（RAMの複製をQEMUから取り出して、ビルドしたイメージのファイルと比べる。以前から在る）。既定の起動は、イメージの全体を歩かない。

**ボリュームの名前の欄を選んだ理由。** この欄は、`e2label`や`dumpe2fs`や`blkid`で見える。人がイメージを手に取ったときに、どのビルドのイメージかが道具で読める。使える欄を4つ比べた。

| 欄 | 見え方 | 採らなかった理由 |
|---|---|---|
| ボリュームの名前（`s_volume_name`。16バイト） | `e2label`・`dumpe2fs`・`blkid`で見える | **採った。** 道具が勝手に書き換えない。人が名前を付ける欄なので、付いていても道具は驚かない |
| UUID（`s_uuid`。16バイト） | `dumpe2fs`・`blkid`で見える | イメージの身元として道具が使う欄である。ビルドを決定的にするために、固定の値を入れてある。中身ごとに変えると、その固定が無くなる。16進の並びで、人には読みにくい |
| 最後にマウントした場所（`s_last_mounted`。64バイト） | `dumpe2fs`で見える | Linuxが、マウントのたびに書き換える。イメージをホストでマウントすると、印が消える |
| スーパーブロックの末尾の予約の領域 | 道具では見えない | e2fsprogsが、後の版で意味を与えうる（ext4は、予約の領域を少しずつ使ってきた）。見えない値は、食い違ったときに気づきにくい |

**ボリュームの名前を、イメージの目印として使っている。** 人がこのイメージに別の名前を付けると（`e2label`で書き換えると）、RAMのイメージから起動したカーネルは、古いイメージと同じ扱いで止まる。

### 5. 壊したイメージの検査は、コピーするのを1回にする

最初に1回だけ、使っている量を作業領域へコピーする。壊し方ごとに、書き換える数バイトの元の値を控え、検査の後で元へ戻す。**戻した後、健全な対照（解析と、5つの読み出し）がもう1度通ることを、壊し方ごとに確かめる。** 「前の壊し方が残らない」を、コピーし直しではなく、戻すことと確かめで保つ。

### 6. ホストの側のイメージは、穴の在るファイルとしてコピーする

検査の道具がイメージをコピーするとき（回ごとの置き場の装置のイメージと、ESPのイメージ）、0だけのブロックを書かずに飛ばす。ファイルの長さは変えない。コピーした後の長さが元と同じであることを、検査が確かめる。

## Alternatives Considered

- **ブロックのキャッシュへ移る**（要るブロックだけを読み、変わったブロックだけを書く）: 今は採らない。ext2の公開の関数のうちイメージを受け取るものが27、カーネルの側でイメージの全体を借りている所が19在り、作り直しになる。読むシステムコールの中で装置を待つ場面もできる。延びた時間の正体は、上の5つで、どれもキャッシュを待たずに外せた。RAM（イメージの大きさだけ要る）と、実機の遅い媒体での保存のために、別の段で扱う。
- **検査値を、全体のまま速くする**（語の単位で計算する）: 採らない。式が変わるので、ホストの側と装置の読みの試験の式も変えることになる。速くなっても、イメージの大きさに比例したままである。
- **検査値を、試験の構成でだけ計算する**: 採らない。既定の起動が「装置から読んだものが、ホストのファイルと同じ」と主張しなくなる。RAMのイメージの取り違えも、既定の起動で見つからなくなる。
- **装置の有無を、ブートローダが調べて、読むかどうかを決める**: 採らない。ブートローダがPCIを調べることになる（「ローダは薄く」。`ADR-0008`）。イメージを置くかどうかは、起動のさせ方を知っている側（検査の道具と、起動媒体を作る側）が決められる。
- **壊したイメージの検査を、管理用の部分だけに絞る**: 採らない。切り出したイメージが、それ自体で読み切れる形でなくなる（検査は、ルートのディレクトリやファイルのブロックも読む）。コピーするのを1回にするほうが、効果が大きく、差分が小さい。
- **起動時の要求を、イメージの全体で1回にする**: 採らない。割り込みを禁じたまま待つ時間が、イメージの大きさに比例して延びる。

## 決めないこと

- ブロックのキャッシュと、変わったブロックだけを書く形（次の段）。
- RAMのイメージから起動する回で、ブートローダがイメージを読む時間（QEMUでは1MiBあたり約0.11秒）。渡されたイメージを別のフレームへコピーせずに、そのまま使う形も、ここでは扱わない。
- セグメントの上限を申告する装置での、実行時の保存（要求を分けて出す形）。

## Consequences

- 起動の時間のうち、イメージの大きさに比例する分が、ほぼ無くなった。残るのは、装置の読み書きの、1MiBあたり約2ミリ秒である。実測は`docs/verification-coverage.md`の「ディスクのイメージの読み書きの所要」に在る。
- 既定の起動が確かめる範囲は、狭くなった。イメージの全体を歩いて検査値を出すことを、やめた。ファイルのブロックが装置から正しく読めたことは、イメージを取り出す検査と、起動時にファイルを読んで中身を比べる確かめが見る。
- 既定の起動のESPは、起動媒体のESPと、イメージの有無が違う形になった。起動媒体の形は、`media-only`と`pc-no-virtio`の変種と、VirtualBoxの判定が見る。
- イメージのボリュームの名前に、意味ができた。
- イメージの全体をRAMに置く形は残っている。RAMは、イメージの大きさだけ要る（RAMのイメージから起動する回は、その2倍）。QEMUのRAMは256MiBなので、イメージを大きくし続けることはできない。
