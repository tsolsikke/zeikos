# 0091. fd の上限を 16 から 32 に上げる

## Status

Accepted（運用者の決定。2026-10-23。C1S4 で実装した）

## Date

2026-10-23

## Context

1 つのプロセスが同時に開ける fd の数（`kernel/src/vfs.rs` の `MAX_OPEN_FILES`）は、S10-b から 16 だった。理由は「見込みの最大が 3 で、その 5 倍を越える余裕」である（同じ定数の doc の「以前の 16 の理由」）。

Seinas のコンポジタは、クライアントが無くても 15 本、タスクバーが 1 つ繋がると 17 本の fd を持つ（Seinas の側の数え方）。クライアント 1 つにつき、接続のソケットと、`SCM_RIGHTS` で受ける共有メモリの fd が増える。16 では、タスクバーが繋がった時点で足りない。

上限を上げるときに縛りになるのは、カーネルのスタックである。fd の表（`FileTable`。1 つの欄が 96 バイト）はプロセスの構造に値で入り、カーネルのスタックに載る。

- 最初に 32 を試したときは、深さ 0 の遠征スタックが syscall-test で 48,856 バイト（74.5%）になった。4 分の 3 のしきい値（49,152 バイト）まで 296 バイトしか残らなかった。デバッグのビルドでは、`spawn` の道に表のコピーが約 10 個載っていたためである。
- 次に 24 を試すと、遠征スタックは 62% に収まった。ところが、切り離したスロットの Ring 3 のタスクのスタック（64 KiB）が 38,728 バイトになり、半分のしきい値（32,768 バイト）を越えて止まった。

そこで先に、`spawn` の道で値で渡していたコピーを除いた（`ADR-0060` の 2026-10-23 の Addendum）。道に残る表は、プロセスの構造の中の本体 1 つになり、上限を 1 つ上げるごとのスタックの増え方は約 960 バイトから 96 バイトになった。24 を選んだ前提が無くなったので、32 にする。

## Decision

1. **`MAX_OPEN_FILES` を 32 にする。** 上限はこの 1 か所で決まる。`prlimit64(RLIMIT_NOFILE)` の答え（ソフトもハードも 32）、`FD_CLOEXEC` の印の幅の確かめ、`MAX_END_HOLDERS` は、どれもこの値から求める。
2. **`FD_CLOEXEC` の印（`FileTable` の `cloexec`）を `u16` から `u32` に広げる。** fd ごとに 1 ビットなので、32 でちょうど収まる。表の大きさは、詰め物の 8 バイトの中に収まるので変わらない（3,088 バイト）。
3. **パイプの端・ソケットの端・listener の数は `u8` のままにする。** `MAX_END_HOLDERS` は 32 で 133 で、255 に収まる。越えればコンパイル時の `assert!` が止める。今のスロットの数と深さなら、`u8` のままで fd の上限 62 まで持つ。
4. **確かめのイメージ `wl-fd-limit-rust` を足す**（`linux-socket-test` のビルドだけが起動時に起こす）。
   - `RLIMIT_NOFILE` の答えが 32 と 32 であること。
   - 表が埋まったときに開いている数が上限と同じこと。
   - `F_DUPFD`・`accept`・`recvmsg` の `SCM_RIGHTS` のそれぞれで、最後の空きには置けて、次は `EMFILE` で断られる（`recvmsg` は fd が渡らない）こと。
   - Linux（WSL）では `RLIMIT_NOFILE` を 32 に下げてから同じことをし、参照（`linux-programs/reference/wl-fd-limit-rust.txt`）と全行を突き合わせる。

### 測ったもの（デバッグのビルド。バイト）

| スタック | 16（値渡しを除いた後） | 32 | しきい値 | 32 の残り |
|---|---|---|---|---|
| Ring 3 のタスク（`pipe-test`。`--with spawn-detached-returns-early` を含む。回ごとの最大） | 23,472〜25,624 | 25,072〜26,728（20 回） | 32,768（半分） | 6,040 |
| 遠征スタック（`syscall-test`。深さ 0） | 25,920 | 27,456 | 49,152（4 分の 3） | 21,696 |
| 遠征スタック（zash。深さ 0） | 26,080〜26,144 | 27,616〜27,680 | 49,152（4 分の 3） | 21,472 |
| 起動時のカーネルスタック（128 KiB） | 68,160 | 68,160 | — | — |

- 16 から 32 で、関数の枠が動いたのは `load_user_program_with`（+1,536 = 16 × 96。プロセスの構造の中の本体）だけだった（`tools/frame-sizes.py`）。
- 起動時のカーネルスタックの最大は、`spawn` の道ではなく Ring 3 へ入る前の道で決まるので、上限では動かない。

### Linux との差（直していない）

表が埋まったときの答え方に、差が 2 つある。確かめのイメージは、両方で同じになる所（最後の空きには置ける、次は断られる・fd が渡らない）だけを判定にしている。

- **`accept`**: Linux は先に fd の空きを見て `EMFILE` を返し、接続は待ち行列に残る（1 つ空ければ、次の `accept` で受けられる。WSL で測った）。ZeikOS は待ち行列から接続を取ってから、表に置けずにその端を閉じる。接続は失われ、相手は EOF を見る。直すときは、`accept` の入口で表の空きを先に見る。
- **`recvmsg` の `SCM_RIGHTS`**: Linux は受けたバイトを返して fd を捨て、`msg_controllen` を 0 にし、`msg_flags` に `MSG_CTRUNC` を立てる。ZeikOS は渡された fd を手放して（`shm::detach`）`-EMFILE` を返す。fd は失われ、バイトは読まずにソケットに残る。`recvmsg` の書き戻しを直すときに、一緒に直す。**2026-10-27 に Linux の形へ直した**（`ADR-0065` の 2026-10-27 の Addendum）。

## Alternatives Considered

1. **24 にする**: 一度はこれに決めた（値渡しのコピーが残っていた時点で、遠征スタックが 62% に収まる値だった）。測ってみると Ring 3 のタスクのスタックが半分を越えたので、値渡しを先に除いた。除いた後は、24 を選ぶ前提（1 つ上げるごとに約 960 バイト増える）が無くなったので、余裕の大きい 32 にした。
2. **表をスロットと深さごとの `static` に置く**: プロセスは添字を持つ形である。スタックから表が消える（`spawn` の道に残る本体 1 つも消える）。カーネルの `spawn` と後片付けの道に触るので、今回はしない。32 より上げるときに先に考える。
3. **遠征スタックか Ring 3 のタスクのスタックを大きくする**: スロットと深さの数だけ `.bss` が増え、ガードページの位置が動く。値渡しを除いた後は要らなくなった。
4. **パイプ・ソケット・listener の数を `u16` に広げる**: 32 では `MAX_END_HOLDERS` が 133 で `u8` に収まり、越えればコンパイル時に止まる。広げると構造の大きさが変わるので、要るときに広げる。

## Consequences

- コンポジタは、タスクバーが繋がった 17 本の形から、あと 15 本の fd を持てる。
- 上限をこれより上げるときは、表の置き場を見直す（Alternatives の 2）。上限を 1 つ上げるごとに、`spawn` の道でスタックが 96 バイト増える。表の大きさの「4 KiB を越えない」テストで、上限は 42 までである。`FD_CLOEXEC` の印は `u32` なので、32 を越えるなら `u64` に広げる。
- `accept` と `recvmsg` の `SCM_RIGHTS` は、表が埋まったときに Linux と違う答え方をする（Decision の「Linux との差」）。
