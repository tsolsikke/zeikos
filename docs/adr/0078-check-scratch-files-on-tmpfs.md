# 0078. 検査の使い捨てのファイルをtmpfsに置き、全検査がSSDに書く量を減らす

## Status

Accepted（2026-10-05に運用者が方針を決め、同じ日に実装した）。

## Date

2026-10-05

## Context

- 作業環境（WSLの仮想ディスク）は、NVMeのSSDの上に在る。SSDへ書く量を減らすことを、運用者が最優先にした。
- 全検査（冷えた状態）が装置へ書く量は、ディスクの像が2MiBのときに53〜61GiB、32MiBにした後は156〜178GiBだった（全検査の記録の実測）。像を大きくしたときに、時間は元へ戻したが（`ADR-0077`）、書く量は戻っていなかった。
- 書く先は、大きく3つである。
  - **QEMUが書くファイル**——装置の像（カーネルは、起動時と保存のたびに、像の全体を装置へ書く。全検査の中の保存は約1,560回）、QEMUから取り出すRAMの像、`-D`の記録、シリアルの記録。
  - **検査の道具が写すファイル**——回ごとのESP（カーネルのELFとブートローダ）、装置の像、起動媒体の像。
  - **ビルドの出力**——カーネルを、破壊テストの構成ごとに1度ずつビルドする（約870組）。増分の置き場だけで、全検査の木に46〜52GiBが在った。
- 同時に走るQEMUは4つまでである（vCPUの数の上限）。作業環境のメモリは15GiBで、`/dev/shm`（tmpfs）は約7.9GiBまで使える。

## Decision

### 1. 回ごとの使い捨てのファイルは、tmpfsに置く

- 装置の像、ESP、起動媒体の像、QEMUから取り出したRAMの像を、`/dev/shm`の下の、回ごとのディレクトリに置く。ログ（シリアルと`-D`の記録）と`run.txt`は、今までどおりSSDの回の置き場に置く。
- **tmpfsの空きが1GiBを切っていたら、その回は今までどおりSSDに置く。** 1回の実行がtmpfsに置くのは、多くて約150MiBである。同時に走るのは4つまでで、項目が終わるまで残す分を入れても、2GiBに届かない見込みである。
- **使い捨てのディレクトリは、回の置き場の値を落とすときに消す。** 検査の項目の中で作ったものは、項目が終わるまで残す（同じ項目の次の起動が、前の起動の装置の像を読む）。
- **SSDへ写すのは、後で要るものだけである。** 項目が失敗したときは、装置の像と取り出した像を、SSDの回の置き場へ写す（0だけのブロックは書かない）。通った項目のものは、写さずに消す。手で打つ起動（項目の外）では、落とすときに写す——前の起動の装置の像を持ち越す流れが、今までどおり動く。既定の像として示した回は、ESPも写す。

### 2. 全検査のビルドは、増分の置き場を使わない

全検査の子のプロセスに`CARGO_INCREMENTAL=0`を渡す。カーネルが変わっていれば、どの組もビルドし直すので、組ごとの増分の置き場はほとんど役に立たない。変わっていなければ、cargoは何もビルドしない。メインの作業ツリーの、手で回すビルドは変えない。

### 3. 古いものは、決まった数だけ残して消す

| もの | 残す量 | いつ消すか |
|---|---|---|
| 回の置き場（丸ごと） | 新しい16個 | 回の置き場を取るたび（以前から） |
| 回の置き場（ログだけ） | 新しい500個（以前は1,000個） | 同じ |
| 全検査のログと、付きの記録 | 新しい10回分 | 全検査を始めるとき |
| 残したカーネルとブートローダの写し | 7日のうちに触られた組 | 全検査を始めるとき |

### 4. 入口の空きの確かめは残し、SSDに書く分だけを見積もる

全検査の入口は、今までどおり、見込みの書く量と下限を、WSLの中と、仮想ディスクの載ったドライブの両方で見る。**見込みは、書く先の作りを変えた時刻より後の記録だけから求める**（それより前の記録には、tmpfsへ移した分が入っている）。新しい記録が無い間は、今までの代わりの値（メインの作業ツリーの`target/`の大きさ）を使う。

### 5. 書いた量を、測って出す

全検査のまとめに、装置へ書いた量の内訳を出す（全体は`/proc/diskstats`の差。QEMUと検査の道具の分は`/proc/<pid>/io`の`write_bytes`。残りがビルドである）。見張り（`cargo xtask full --watch`）は、始まってから書いた量と、仮想ディスクの載ったドライブの空きを出す。

## Alternatives Considered

- **`target/`の全体をtmpfsに置く**: 採らない。ビルドの出力は数十GiBで、メモリに載らない。
- **ログもtmpfsに置く**: 採らない。失敗の調べに要る。`-D`の記録は、例外が続く検査で数百MiBになることが在り、大きさが読めない。
- **失敗したかどうかに依らず、装置の像をSSDへ写す**: 採らない。写しは小さい（0だけのブロックを書かなければ、数MiB）が、通った回の像は、後で誰も読まない。
- **検査用のビルドのデバッグ情報を減らす**: 今は採らない。効果は見込める（構成ごとのカーネルと、その依存の出力が小さくなる）が、スタックの深さを測る道具と、フレームの大きさの検査が、デバッグ情報を読む。何が読めなくなるかを確かめてから決める。
- **残したカーネルの写しを、写しではなくハードリンクにする**: 今は採らない。写しは、同時に走る実行が書きかけを読まないための仕組みで（別の名前へ写してから置き換える）、リンクにすると、その守りの前提が変わる。

## 決めないこと

- 保存のたびに像の全体を書くこと自体は、変えていない（変わったブロックだけを書く形は、ブロックのキャッシュの段で扱う）。tmpfsへ移したので、検査の間は、SSDへは届かない。実機や、手で起動して使う場面では、今までどおり装置へ書く。
- 検査用のビルドのデバッグ情報と、最適化の段。

## Consequences

- 全検査がSSDへ書く量が減った。実測は`docs/verification-coverage.md`の「全検査がSSDに書く量」に在る。
- 通った回の装置の像は、残らなくなった。後から像を見たいときは、その項目を手で打ち直す（手で打つ起動は、像をSSDへ写す）。
- 全検査の間、tmpfsを2GiBほど使う。メモリが足りないときは、空きの確かめが、その回をSSDへ戻す。
- 全検査のビルドは、増分の置き場を使わないので、カーネルを少しだけ変えた後の全検査でも、どの組も初めからビルドする（今までも、組ごとの置き場が在るだけで、ほとんど同じだった）。
