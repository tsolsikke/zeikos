# 0079. 遠征スタックの下に見張りのページを張り、あふれたスタックを名指しして止まる

## Status

Accepted（2026-10-06に運用者が設計案を承認し、同じ日に実装した）。

## Date

2026-10-06

## Context

- 遠征スタックは、Ring 3のプログラムがカーネルへ入ったときに使うカーネル側のスタックである。スロットと深さごとに1本ずつ、4本を持つ。1本は64KiBである。
- このスタックだけ、下に見張りのページが無かった。`.bss`の配列で、ページの境界に揃っていなかったためである。代わりに、最下部の256バイトを埋めた値で見ていた。この形は、プログラムが戻ってから気づく。あふれた先の静的な領域は、そのときにはもう書かれている（S11-5で実際に踏んだ。`docs/troubleshooting.md`）。
- その代わりとして、「使用量が容量の半分を越えたら止まる」という線を置いていた（S11-6）。見張りのページを張るか、容量を上げるかを、越えた時点で決めるための合図である。
- 2026-10-06に、余りが尽きかけた。全検査の中の最大は32,504バイトで、線（32,768バイト）まで264バイトだった。実行ファイルを範囲で読んで載せる変更の途中では、いちど線を越えてカーネルが止まった。載せる側の枠を少し太らせるだけで止まる状態になっていた。
- 深く使うのは、`spawn`の経路である。親が`spawn`を呼んで子が走っている間、親の遠征スタックに、載せる側の枠（`spawn`、`run_loaded_program`、`load_user_program_from`など。合わせて約26KiB）が積まれたままになる。
- ほかのカーネルのスタック（起動のカーネルスタック、ワーカー、BSPのアイドル、Ring 3のタスクのカーネルスタック、APのスタック）は、どれも下に写していない1ページを持っている。ページフォルトはIST2で受けるので、見張りのページに当たっても、ダブルフォルトにはならない。
- ただし、ページフォルトのハンドラが名指ししていたのは、起動のカーネルスタックの見張りだけだった。ほかのスタックのあふれは、「カーネルスタックの見張りの中ではない」としか出なかった。

## Decision

### 1. 遠征スタックを、ほかのスタックと同じ形にする

- 1本を、見張りの1ページと本体64KiBの組にして、ページの境界に揃える。置き場は`.bss`のままである。
- 起動時に、4本の下の1ページを外す。最初の遠征より前に行う。外す手順は、ほかのスタックと同じ1つの関数（`install_guard_page`）を使う。
- 外した後に、4本とも、写っておらず、自分の名前で控えられていることを、今のページテーブルと控えの表から読んで確かめる。欠けていれば、名指しして止まる。
- 最下部の256バイトの区間と、「無傷か」の判定は消す。埋めた値で使用量を測る仕組みは残す。

### 2. 見張りのページを表に控え、ページフォルトのハンドラが名前を出す

- 見張りのページの番地と、その上に在るスタックの種類を、小さな表（64欄）に控える。外す関数が控える。APのスタックの下の穴（初めから写さない形）も、写す所で控える。
- ページフォルトのハンドラは、落ちた番地を表から引いて、どのスタックがあふれたかを1行で出す。表はロックを取らずに読める形にしてある。
- カーネルの像の区画の確かめ（写っていないページを認めるのは見張りのページだけ）も、この表から引く。

### 3. 容量は64KiBのまま、止まる線を4分の3へ移す

- 実測の最大（約32.5KiB）に対して、余りは約33KiBである。必要な量とほぼ同じだけ余る形で、起動のカーネルスタックを128KiBに決めたときと同じ比である。
- 線の意味が変わった。あふれは見張りのページが止めるので、線は、その手前で「余りが減った」と知らせる役になる。4分の3（49,152バイト）にすると、今の最大から約16KiBの伸びしろが在り、線を越えてもまだ16KiB残る。
- 使用量が線に近づいたら、最初に、プロセスの記録をスタックから外す（下の「採らなかった案」の3）。

## Alternatives Considered

1. **フレームから取って、専用の番地へ写す**（APのスタックと同じ形）: 今は採らない。`.bss`が256KiB減り、容量を変えてもカーネルの像が動かない利点が在る。ただ、番地の区画を足し、どのプロセスの空間からも見えることを確かめる必要が在り、差分が大きい。`docs/deferred-decisions.md`に行を置いた。
2. **容量を96KiBへ上げて、線を半分のままにする**: 採らない。`.bss`が128KiB増える。見張りのページが入れば、半分の線を保つ理由（あふれを先に知る手段がほかに無い）が無くなる。
3. **載せる側の枠を先に減らす**（プロセスの記録をスタックから外す、道の名前と引数の写しを借りたフレームへ移す、判定の行を組む部分を別の関数へ出す）: 今は行わない。見張りのページが無いまま余りを増やしても、次に尽きたときに同じ形になる。先に見張りのページを張り、減らすのは、測ってから別の刻みで行う。`docs/deferred-decisions.md`に行を置いた。
4. **BSPのISTのスタック5本も、同じ変更で見張りのページにする**: 分ける。こちらは下に4KiBの犠牲の領域とカナリアを持っていて、遠征スタックほど差し迫っていない。`docs/deferred-decisions.md`に行を置いた。

## Consequences

- 遠征スタックのあふれは、その瞬間にページフォルトになり、スタックの名前つきで止まる。下の静的な領域は書かれない。
- ワーカー、アイドル、Ring 3のタスクのカーネルスタック、APのスタックのあふれにも、名前が付く。
- `.bss`が16KiB増え、起動ログに9行増える（外した2行が4本分と、確かめの1行）。
- 止まる線が4分の3になったので、載せる側の枠を足せる余地が、264バイトから約16KiBになった。
- 表は64欄である。BSPの側で9枚、APの1つにつき6枚を使う。BSPの側は、一杯なら止まる。APの穴は、一杯でも止めずに警告を出す（スタックは使える。名指しが出ないだけである）。
- 破壊テストを5つ足した——深さ0と深さ1の遠征スタックをあふれさせる形、見張りのページを張らない形、名指しの表に控えない形、止まる線を越える深さまで使う形。
