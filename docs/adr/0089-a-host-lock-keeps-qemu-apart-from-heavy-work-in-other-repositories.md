# 0089. ホストのロックで、ZeikOSのQEMUと別のリポジトリの重い作業を重ねない

## Status

Accepted（運用者の決定。2026-10-20。ZeikOSの側を実装した。Seinasの側は、SeinasのCLAUDE.mdとpre-pushで後から入れる）

## Date

2026-10-20

## Context

ZeikOSとSeinasは、同じWSLのディストリで別々に開発している。Seinasの大きなビルドとZeikOSのQEMUが重なると、QEMUの時間が延びる。
すると、ティックの位置と遅さの計測が揺れる。起票済みの揺れる項目の1つでは、落ちた回のホストのCPU利用率が48%で、通った回は20〜32%だった。

これまでは、全検査を始める前に`pgrep`で1回確かめるだけだった（`qemu-system-x86`と、`cargo`・`rustc`の行）。この確かめは
運用者の作業の指示に書かれていただけで、`CLAUDE.md`には無かった。始めた後に相手が重い作業を始めても見えない。
それに、相手の側からはZeikOSのQEMUが見えない。

検査のロック（`ADR-0069`の決定7の3。`xtask/src/check_lock.rs`）は、ZeikOSの中の並行だけを見る。置き場がgitの共通の
置き場なので、別のリポジトリからは見えない。

## Decision

1. **置き場は`/tmp/zeikos-qemu.lock`に固定する。** 同じディストリの中なら、どのリポジトリからも同じパスである。環境変数で
   置き場を変えない（変えると、片方だけが別のファイルを見て、排他が黙って外れる）。**無ければ作る。** `/tmp`は再起動で消えて
   よい。誰も持っていない間に消えても、次に開いた者が作り直すだけである。
2. **取り方は`flock`である。**
   - **ZeikOSは、QEMUを使う間、共有（`LOCK_SH`）で持つ。** ZeikOSの中の並行の実行（`run-set`の子どうしなど）は、互いに妨げない。
   - **重い作業をする側は、排他（`LOCK_EX`）で取れるまで待つ。** `flock -x /tmp/zeikos-qemu.lock <コマンド>`で足りる。
   - こうすると、2つの向きの両方が成り立つ。ZeikOSのQEMUが1本でも動いている間は、重い作業が待つ。重い作業の間は、ZeikOSの
     QEMUが待つ。
3. **ZeikOSの新しい取得は、排他を待っている者が居れば先に譲る。** Linuxの`flock`は、排他が待っている間も新しい共有を通す
   （2026-10-20に`flock(1)`で確かめた）。譲らなければ、ZeikOSが実行を続ける間、重い作業がいつまでも待つ。待っている者は
   `/proc/locks`の`->`の行で見える。**ただし、祖先がこのロックを持っているときは譲らずに取る。** 譲ると、祖先が子の終わりを待ち、
   排他を待つ者が祖先を待ち、子が排他を待つ者を待つ、という輪になる。
4. **ZeikOSの側には、待つ上限がある。** 普通の実行（`run`・`run-set`の子・`check --commit`など）は10分、全検査は60分である。
   越えたら、検査のロックと同じ終了の値75で断る。コミットの後のhookは900秒で切られるので、黙って待ち続けない。待つ間は、
   1分ごとに`host lock:`で始まる行を出す（誰が持っているか、誰が待っているか）。
5. **検査のロックとは別のファイルにする。** 取る順は、検査のロック、ホストのロックの順である。検査のロックは誰も待たない
   （取れなければすぐ断る）ので、この順で輪はできない。重い作業の側は、ホストのロックしか取らない。
6. **ZeikOSの側で取る所は、検査のロックを自分で取った所と同じである**（`check_lock::hold`。QEMUを使う入口と、QEMUを起こす
   唯一の入口`launch::spawn`）。全検査は親が排他の検査のロックを取った後に取り、終わるまで持つ。全検査の中の子は取らない
   （親が持っている）。
7. **持ち主が落ちても、ロックは残らない。** `flock`は、プロセスが終われば（SIGKILLを含む）カーネルが放す。ファイルに中身は
   書かない（共有の持ち主が並ぶため）。持ち主は`/proc/locks`から読む。`cargo xtask full --status`が持ち主と待つ者を出す。
8. **ロックのファイルは、開くたびに更新時刻を進める。** `/tmp`の掃除（30日）が、持たれているファイルを消さないようにする
   ためである。消えると、次に開いた者が別のファイルを作り、排他が外れる。

### 重い作業をする側の約束（Seinasの側がコピーする）

- 重い作業（大きなビルド、まとめたテスト、ベンチマークなど）は、`flock -x /tmp/zeikos-qemu.lock <コマンド>`で包む。
- 待つ間に何も出ないと、止まっているのと区別できない。先に`flock -x -n`で試し、取れなければ1行出してから待つ。
  例: `flock -x -n /tmp/zeikos-qemu.lock true || echo "waiting for ZeikOS's QEMU"`。
- 上限を付けるなら`flock -x -w <秒>`。全検査は1時間ほど（2026-10-20は69分）かかるので、全検査の間に始めた重い作業は、それだけ待つ。
- ロックのファイルに書き込まない。消さない。

## Alternatives Considered

- **`pgrep`の1回の確かめのままにする。** 確かめた後に始まった重なりが見えない。相手の側からZeikOSのQEMUも見えない。
- **検査のロックと同じファイルにする。** 置き場がgitの共通の置き場で、別のリポジトリからは見えない。それに、検査のロックの
  排他は全検査の意味を持っている。Seinasが排他で取ると、ZeikOSの実行は待たずに断られる。
- **置き場を`~/.cache`の下にする。** `HOME`は環境変数で、hookの環境では変わりうる（検査のロックが`~/.cache`を採らなかった
  のと同じ理由）。
- **ZeikOSも、取れなければ待たずに断る。** 重い作業は数分で終わることが多い。断ると、そのたびに人が始め直すことになる。
  待つほうが、運用の手間が少ない。上限を付ければ、ハングと区別できる。
- **上限なしで待つ。** 背景の実行には道具の側の上限（2時間）がある。上限なしで待つと、切られたのか待っているのかが区別できない。
- **待っている排他に譲らない。** 運用が簡単になるが、ZeikOSの`run-set`が続く間、Seinasが待ち続ける。
- **QEMUを1本起こすたびに取り、終わるたびに放す。** 全検査の項目の合間に重い作業が入り込むと、後の項目が待つ。そのうえ、
  全検査の途中でホストの負荷が変わる。全検査は計測でもあるので、始めから終わりまで持つ。

## Consequences

- 全検査の間に始めた重い作業は、全検査が終わるまで待つ。逆に、重い作業の間に始めた全検査は、最長60分待ってから断られる。
- ZeikOSの中の並行の実行は、今までどおり互いに待たない。
- `xtask`だけが止められてQEMUが残ると、QEMUが走っている間もロックは放れている（ファイルはQEMUに渡らない）。検査のロックと
  同じ限界である。
- **Seinasの側が排他で取るようになるまでは、ZeikOSが共有で持っても守りにならない。** それまでは`pgrep`の確かめを残す
  （`CLAUDE.md`の「Seinasの重い作業と重ならないように」）。
- 確かめは、`xtask/src/host_lock.rs`のホストのテスト（`/proc/locks`の読み方、譲る判断、上限）と、2026-10-20の生きた確かめ
  （`docs/verification-coverage.md`の「ホストのロック」）である。
