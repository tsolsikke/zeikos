# 0076. FSとGSの基底を、FPの状態と同じ組で文脈ごとに持つ。`arch_prctl`を足す

## Status

Accepted（2026-10-05に運用者が設計を承認し、同じ日に実装した）。

## Date

2026-10-05

## Context

- Linux向けのプログラム（muslやRustの標準ライブラリでビルドしたもの）は、スレッドローカルの領域（TLS）をFSの基底から引く。基底は、起動の早い段階で`arch_prctl(ARCH_SET_FS)`で入れる。これが無いと、最初のSeinasのプログラムは`main`へ着く前に止まる（`ADR-0074`の棚卸し）。
- ZeikOSのカーネルは、`fs:`も`gs:`も`swapgs`も使っていない（`ADR-0075`の決定1）。FSとGSの基底は、誰も入れず、誰も保存していなかった。
- ユーザーのプログラムは、タスクの上で走る。タスクが切り替わるとき、プログラムを走らせる直前、子を起動する前後の3か所で、FPの状態を保存・復元している（`ADR-0058`）。
- `CR4.FSGSBASE`は0に保っている（`ADR-0018`のAddendum 9の棚卸し）。Ring 3が`wrfsbase`や`wrgsbase`を打つと`#UD`になる。

## Decision

### 1. FPの状態と、FS・GSの基底を、1つの組にする

「ユーザーの実行の文脈が持つレジスタ」という1つの型（`UserRegisters`）にまとめ、保存と復元の関数も1組にした。置き場はタスクごとで、FPの状態が在った所をそのまま使う。

**理由。** 保存と復元が要る場面が、FPの状態と基底で同じだからである——タスクの切り替え、プログラムを走らせる直前、子を起動する前後。置き場を別にすると、入れ替える所が2系統になり、片方だけ忘れる形ができる。1つの型にしておけば、次に足すレジスタも同じ3か所に入る。

置き場をプロセスではなくタスクに付けたのは、スレッドのためである。スレッドが入ると、スレッドごとにタスクを持つ。この組は、そのままスレッドごとのものになる。プロセスが持つもの（アドレス空間・ファイルの表・ヒープと`mmap`の番地）とは分けてある。

新しいプログラムは、FPが既定の状態、基底が0から始まる。子は、親の基底を引き継がない。

### 2. 出る側では、控えた値を信じずに、レジスタから読んで保存する

`arch_prctl`で入れた値を別に控えておき、それを保存の値にする形は採らなかった。保存のたびに、MSRから読む。

**理由。** ユーザーは、`arch_prctl`以外でも基底を変えられる。FSやGSに区画のセレクタを載せ直すと、Intelの石では基底が0になる。控えた値を戻すと、ユーザーが見ていた状態と違うものを戻すことになる。レジスタから読めば、控えと実際がずれる形そのものが無い。後で`CR4.FSGSBASE`を立てても（ユーザーが命令で基底を書けるようになる）、置き場と入れ替えの位置は変わらない。

### 3. MSRで読み書きする。`CR4.FSGSBASE`は0のままにする

基底は、`IA32_FS_BASE`と`IA32_GS_BASE`を`rdmsr`・`wrmsr`で読み書きする。`rdfsbase`・`wrfsbase`の命令は使わない。

**理由。** `CR4.FSGSBASE`を立てると、Ring 3が命令で基底を書けるようになる。棚卸し（`ADR-0018`のAddendum 9）が0に依っているビットを、速さを測らないまま動かさない。MSRは、長モードのCPUに必ず在る。切り替えのたびに読み2つと書き2つが増えるが、費用は測っていない。問題になったときに、測ってから決める。

### 4. 基底にしてよいのは、ユーザーの範囲の番地だけである

`ARCH_SET_FS`と`ARCH_SET_GS`は、番地がユーザーの番地の上限（`0x0000_7fff_ffff_f000`。`ADR-0075`の決定5）より下でなければ、`-EPERM`を返して何も変えない（Linuxと同じ値）。カーネルの番地と、正準でない番地を断る。

**理由。** 正準でない値を基底のMSRへ書くと、カーネルの中で一般保護例外になる。確かめが無ければ、ユーザーがカーネルを止められる。復元の側は確かめない——入れる側がユーザーの範囲だけを通し、保存はレジスタから読むので、保存された値は、通した値か、ユーザーがセレクタを載せ直して0になった値である。

### 5. GSも、ユーザーに使わせる

`ARCH_SET_GS`と`ARCH_GET_GS`も受け、GSの基底もFSと同じに保存・復元する。

**理由。** カーネルがGSを使っていないので、断る理由が無い。Linuxのプログラムから見て、4つとも使える形がLinuxと同じである。

**将来`swapgs`を入れると決めたら、ここは作り直しになる。** `swapgs`を使うカーネルでは、Ring 0に居る間、`IA32_GS_BASE`はカーネルのCPUごとのデータを指し、ユーザーの基底は`IA32_KERNEL_GS_BASE`の側に在る。いまの「`IA32_GS_BASE`を読んで保存し、書いて復元する」は、そのままではカーネルの基底を読み書きする。保存・復元と`arch_prctl`のGSの側を、`IA32_KERNEL_GS_BASE`へ向け直す必要がある。FSの側は変わらない。`swapgs`へ移るかどうかは、CPUの数を増やす段で決める（`ADR-0075`の決定1）。

### 6. `arch_prctl`の形

- 番号は158（Linuxのx86_64と同じ）。`ARCH_SET_GS`（`0x1001`）・`ARCH_SET_FS`（`0x1002`）・`ARCH_GET_FS`（`0x1003`）・`ARCH_GET_GS`（`0x1004`）を受ける。
- 訊く側は、2つ目の引数が指す番地へ8バイトを書く。書けない番地なら`-EFAULT`を返す。
- それ以外の`code`は`-EINVAL`を返す（Linuxと同じ）。CETやCPUIDの制御などの`code`は、要るプログラムが出たときに足す。

## Alternatives Considered

- **基底を、FPの状態とは別の置き場に持つ**: 採らない。入れ替える所が2系統になる。
- **基底をプロセスごとに持つ**: 採らない。スレッドが入ると、スレッドごとに違う値になる。後で移すより、最初から実行の文脈に付ける。
- **`arch_prctl`で入れた値を控え、それを復元する**（レジスタから読まない）: 採らない。ユーザーがセレクタを載せ直して基底を変えると、控えと実際がずれる。
- **`CR4.FSGSBASE`を立てて、命令で読み書きする**: 今は採らない。Ring 3からも基底を書けるようになり、棚卸しの前提が1つ動く。MSRの読み書きの費用を測っていない。
- **GSはユーザーに使わせない**（`ARCH_SET_GS`を断る）: 採らない。カーネルが使っていない間は、断る理由が無い。`swapgs`を入れる段で作り直す費用は、決定5に書いた。
- **復元の側でも、番地を確かめる**: 採らない。入れる側と保存の仕方で、正準であることが決まる。切り替えのたびに確かめを足すことになる。

## 決めないこと

- `CR4.FSGSBASE`を立てるかどうか。
- `swapgs`へ移るかどうか（`ADR-0075`）。移るときのGSの側の作り直し。
- TLSの領域そのものを、カーネルが用意するかどうか。静的リンクのプログラムは、自分で領域を取り、`PT_TLS`の中身を写してから基底を入れる。カーネルがすることは、基底を入れて保つことだけである。
- スレッドを作るときに基底を渡す道（`clone`の`CLONE_SETTLS`）。スレッドを入れる段で決める。

## Consequences

- Linux向けのプログラムが、TLSの基底を入れられるようになった。入れた基底は、タスクの切り替えと、子の起動を跨いで保たれる。
- ユーザーが変えられるCPUの状態が、2つ増えた（FSとGSの基底）。カーネルはどちらも使わないので、カーネルの側の前提は増えていない。`fs:`・`gs:`・`swapgs`が0個であることの見張りは、そのままである。
- タスクの切り替えのたびに、MSRの読みが2つ、書きが2つ増えた。ユーザーを走らせないタスク（ワーカーとアイドル）でも行う（値は0のままである）。
- 本物の石での振る舞いのうち、QEMUで確かめられないものが1つ増えた。正準でない値を基底のMSRへ書くと、本物の石ではカーネルの中で`#GP`になるが、QEMUのTCGは例外にせずに受ける（実測）。番地を確かめない破壊テストは、QEMUでは「断られずに通ってしまう」ことで見ている。
- APの上での保存と復元は、まだ通る者が居ない（APはユーザーのプログラムを走らせない）。
- 検査と実測は`docs/verification-coverage.md`の「FSとGSの基底と`arch_prctl`」に在る。
