# 0075. `syscall`命令を入口に足す。`swapgs`を使わず、戻りは`iretq`にする

## Status

Accepted（2026-10-04に運用者が設計を承認し、同じ日に実装した）。

## Date

2026-10-04

## Context

- Linux向けのプログラム（muslやRustの標準ライブラリでビルドしたもの）は、システムコールを`syscall`命令で呼ぶ。ZeikOSの入口は`int 0x80`だけで、`EFER.SCE`を0に保ち、立っていれば起動を止めていた。Linuxのプログラムをそのまま動かすと決めたので（`ADR-0074`）、`syscall`命令を受ける入口が要る。
- `int 0x80`の入口は残す（`ADR-0074`の決定3）。いまのユーザープログラムと検査は、その上に在る。
- `syscall`命令は、割り込みの入口と違って、CPUがスタックを切り替えない。入った時点のRSPはユーザーの値のままで、レジスタも全部ユーザーの値である。カーネルのスタックの番地を、レジスタを壊さずに手に入れる方法を決める必要がある。
- ZeikOSのカーネルは、`fs:`も`gs:`も`swapgs`も使っていない。CPUごとのデータは、LAPICのIDで引く配列に置いている。「使っていないこと」は基本の検査が逆アセンブルで数えていて、ユーザーが変えられるCPUの状態の棚卸し（`ADR-0018`のAddendum 9）の前提になっている。
- ユーザーのプログラムは、BSPでだけ走る。CPUの数の上限（`MAX_CPUS`）は2である。

## Decision

### 1. スタックの切り替えは、CPUごとのスタブで行う。`swapgs`は使わない

- CPUごとに短いスタブを1つずつ持つ。`LSTAR`はCPUごとのレジスタなので、CPUごとに自分のスタブを指させる。
- スタブは、ユーザーのRSPを自分のCPUの退避の欄へ置き、**そのCPUのTSSのRSP0を、RIP相対で直に読んで**RSPへ入れる。`int 0x80`で入ったときにCPUが切り替える先と、同じ欄である。
- 切り替えた後は、割り込みで入ったときにCPUが積むのと同じ5語（SS・RSP・RFLAGS・CS・RIP）と目印を自分で積み、`int 0x80`の共通の経路へ合流する。退避・呼び出し・復元と、番号表は、どちらの入口でも同じである。

**理由。**

- カーネルのスタックの番地を写して持たない。RSP0は、ユーザーのプログラムの入れ子やタスクの切り替えで動く。TSSの欄を直に読めば、合わせる所が増えない。
- `fs:`・`gs:`・`swapgs`を使わないままでいられる。`swapgs`は、Ring 3から来たすべての入口と出口で対にする必要があり、NMIでは「どちらのGSか」を見分ける処理が要る。対が崩れると、ユーザーが決めた番地をカーネルがCPUごとのデータとして読む。割り込みと例外の3つの入口に手を入れずに済むことを重く見た。
- ユーザーは、FSとGSの両方を自由に使える。TLSのためのFSの基底は、MSRを書くだけで足りる。

**欠点。** CPUの数だけスタブが要る。いまは2つで、数が変わるとビルドが止まるようにしてある。**CPUの数を増やす段（2 CPU以上）で、この形を見直す**——スタブを数だけ並べ続けるか、`swapgs`へ移るかを、その段で決める。

### 2. 入るときに落とす旗（SFMASK）

`0x47700`を入れる。IF（ユーザーのRSPの上で割り込みを受けない）、TF（入口の最初の命令で、Ring 0のままデバッグ例外を受けない）、DF（コピーの向きをユーザーに決めさせない）、AC（SMAPを入れる段で、入口に`clac`を足さずに済む）、NT（立ったまま入ると、出口の`iretq`が`#GP`になる）、IOPLである。

### 3. NMI・機械チェック・デバッグ例外は、専用のスタック（IST）で受ける

スタブの最初の2命令の間は、Ring 0のままユーザーのRSPで走る。割り込みはIFを落とすので届かないが、この3つは届く。ISTを使わなければ、CPUはユーザーが決めた番地へフレームを積む。**入口を足す前に、3つともISTへ移した**（IST3・IST4・IST5。CPUごとに別のスタック）。3本を分けたのは、ISTが入るたびに同じ頂点から積むので、同じ番号を分け合うと、片方の処理中に届いたもう片方が前のフレームを上書きするためである。

### 4. 戻りは`iretq`だけにする

- `int 0x80`と同じ出口を通って、`iretq`で戻る。`sysretq`は使わない。
- `sysretq`は、戻り先（RCX）が正準でない番地のとき、Intelの石ではRing 0のまま`#GP`を起こす。そのときRSPは、既にユーザーの値である。`iretq`では、この形は起きない。
- `iretq`で戻っても、RCXには戻り先、R11にはRFLAGSが入った状態で戻る。Linuxのプログラムから見た形は、`sysretq`で戻る場合と同じである。
- **`sysretq`を入れるかどうかは、別に測ってから決める。** 入れるなら、戻り先が正準であること、RCXとRIP・R11とRFLAGSが一致すること、CSとSSが既定の値であることを全部確かめ、外れたら`iretq`へ回す形にする。

### 5. 戻る直前に、戻り先を確かめる。ユーザーの番地の上限を決める

- Ring 3へ戻る直前に、フレームの戻り先が**`0x0000_7fff_ffff_f000`より下**であることを確かめる。違えば、戻らずに、そのプロセスを終わらせる（一般保護例外として記録する）。`int 0x80`から来た場合も、同じ所を通る。
- `iretq`も、戻り先が正準でなければカーネルの中で`#GP`になる。確かめずに戻れば、ユーザーがカーネルを止められる。
- **ユーザーの番地の上限は`0x0000_7fff_ffff_f000`とする**（Linuxの`TASK_SIZE_MAX`と同じ値）。正準な番地の下半分の、最後の1ページを使わせない。最後のページの末尾に`syscall`命令を置くと、戻り先（命令の次の番地）が正準でなくなるためである。いまは、そこへ写す手段が無い。番地を指定する`mmap`を入れる段で、写す側の決まりにする。**→ 番地を指定する`mmap`は`ADR-0082`で入ったが、写す側の決まりは無いままだった。2026-10-07に入れた**（`ADR-0082`のAddendum）。
- **シグナルから戻る経路（`rt_sigreturn`）を入れるときは、この所でRIPだけでなくCS・SS・RFLAGSも確かめる。** その経路では、戻すレジスタの中身をユーザーが用意する。いま確かめがRIPだけで足りるのは、CS・SS・RFLAGSを、CPUかスタブが積んだ値のまま戻しているからである。

### 6. 互換モードからの`syscall`は、プロセスを終わらせる

GDTには、32ビットのユーザーのコード区画が在る（`sysret`の並びのために空けられない。`ADR-0020`）。Ring 3はそこへ移って`syscall`命令を打てる。Intelの石では`#UD`になり、今までどおり畳まれる。AMDの石では`CSTAR`の飛び先へ来るので、そこにも同じ形でスタックを切り替えるスタブを置き、そのプロセスを終わらせる（無効な命令の例外として記録する）。

**ここはLinuxとの差である。** 32ビットの呼び出しに対応していないLinuxは、互換モードの`syscall`に`-ENOSYS`を返して戻る。ZeikOSは、戻らずにプロセスを終わらせる。32ビットは使わない（`docs/architecture.md`の「ABIの形は合わせる」）ので、返して続けさせる道を作らなかった。

### 7. `EFER.SCE`の見張りは、読み戻しへ置き換える

「`EFER.SCE`は0であるべき。立っていれば止まる」を、「SCEは1で、STAR・LSTAR・CSTAR・SFMASK・`IA32_SYSENTER_CS`が決めた値である」へ置き換えた。起動のたびに、BSPとAPがそれぞれ読み戻し、あるべき値と並べて起動ログに出す。違えば止まる。MSRを先に書き、SCEを最後に立てる（BSPもAPも同じ順）。

## Alternatives Considered

- **`swapgs`でCPUごとのデータを引く**（Linuxと同じ形）: 今は採らない。CPUの数に依らない利点は在るが、3つの入口すべてに対の`swapgs`が入り、「`fs:`・`gs:`・`swapgs`が0個」の見張りを手放すことになる。CPUが2つの間は、スタブを2つ並べるほうが小さい。CPUの数を増やす段で見直す。
- **カーネルのスタックの番地を、別の欄に写して持つ**: 採らない。RSP0を書く所すべてで、写しも書く必要が出る。書き忘れると、`int 0x80`と`syscall`命令で別のスタックに入る。
- **最初から`sysretq`で戻る**: 採らない。速さの利点を測っていない。正準でない戻り先の扱いを誤ると、Ring 0のままユーザーのRSPで例外を受ける。入口を足すことと、戻り方を変えることは、別の判断にした。
- **`syscall`命令へ移した時点で`int 0x80`を閉じる**: 採らない（`ADR-0074`）。
- **互換モードの`syscall`に`-ENOSYS`を返す**（Linuxと同じ）: 採らない。32ビットのコードへ戻す出口を、使わないもののために作ることになる。
- **GDTから32ビットのユーザーの区画を外す**: 採らない。`sysret`の区画の並びが崩れる（`ADR-0020`）。

## 決めないこと

- `sysretq`を使うかどうか。
- `int 0x80`を消す時期（`ADR-0074`）。
- CPUの数を増やしたときの、スタックの切り替え方。
- NMIから戻る処理を書くときの、入れ子の扱い（いまのNMIの処理は、レジスタを出して止まる）。

## Consequences

- Linux向けのプログラムが打つ`syscall`命令が、カーネルへ届くようになった。番号表は`int 0x80`と同じなので、入っているシステムコールは、どちらの入口からも同じ結果を返す。Linuxのプログラムが実際に動くには、実行ファイルの読み方、TLS、シグナル、メモリの呼び出しなどが、まだ要る（`ADR-0074`）。**→ TLSは`ADR-0076`、読み方は`ADR-0080`、メモリの呼び出しは`ADR-0082`で入り、2026-10-06にM1、2026-10-07にM2が通った。残るのはシグナルの配送である**（当時の記述として残す）。
- カーネルへ入る道が1つ増えた。入口の確かめ（方向の旗・スタックの境界・BKL）は、共通の経路に在るので、両方の入口に効く。加えて、システムコールの入口で「カーネルへ入ったスタックが、ユーザーのプログラムを走らせるためのカーネル側のスタックの中に在ること」を確かめるようにした。
- 本物のIntelの石での振る舞いのうち、QEMUで確かめられないものが残っている。互換モードの`syscall`が`#UD`になること、正準でない番地への`iretq`がカーネルの中で`#GP`になることである（QEMUのTCGは、前者を`CSTAR`へ届け、後者をRing 3へ移ってからのページフォルトにする。実測）。戻り先の確かめは、どちらの振る舞いでもプロセスを先に終わらせる。
- APのスタブは、まだ通る者が居ない（APはユーザーのプログラムを走らせない）。MSRが自分のスタブを指していることだけを、読み戻しで見ている。
- 検査と実測は`docs/verification-coverage.md`の「`syscall`命令の入口の試験と破壊テスト」と「デバッグ例外・NMI・機械チェックをISTへ移した」に在る。
