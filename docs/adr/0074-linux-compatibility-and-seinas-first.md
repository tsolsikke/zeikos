# 0074. Linuxカーネルと完全互換にし、Seinasを動かすことを先に行う

## Status

Accepted（2026-10-04に運用者が決定した）。

## Date

2026-10-04

## Context

- これまでは「ABIの形はLinuxに合わせるが、Linuxのバイナリをそのまま走らせることは目標にしない」としていた（2026-09-17の運用者の決定。`docs/architecture.md`の「ABIの形は合わせる」）。走らせるかどうかは未決のまま残していた（`ADR-0069`の決定4の5）。
- 段階の順序は、境界の段階 → ARMの浅い仮対応 → BKLの出入口 → システムコールの入口・スレッド・シグナル → 2 CPU以上 → 実機対応 → Seinas、だった（`ADR-0069`の「段と順序」）。Seinasは最後に置いていた。
- 境界の段階は2026-10-03に締めた（`ADR-0071`）。次に何を行うかを決める時点で、運用者が方針を見直した。
- Seinasは、Smithayを使うRust製のWaylandコンポジタとして、まずLinuxの上で作る（`ADR-0067`）。Rustの標準ライブラリとSmithayは、Linuxのシステムコールをそのまま呼ぶ。ZeikOSの上で動かすには、ZeikOSの側をLinuxに合わせるか、Seinasの側をZeikOS専用に書き分けるかのどちらかになる。
- 2026-10-04に、いまのZeikOSとの差を棚卸しした。Linux向けに静的リンクしたRustのプログラムは、起動から表示までに40種ほどのシステムコールを使う（実測。最小のクライアントで、起動時に28種、表示を続ける間に13種）。ZeikOSが持つLinuxの番号のシステムコールは26個で、形が合うものはその一部である。入口の命令（`syscall`）、実行ファイルの形（位置独立の静的リンク）、TLS、シグナル、無名の`mmap`などが足りない。

## Decision

1. **ZeikOSのカーネルは、Linuxカーネルと完全互換にする。** Linux向けに作ったCやRustのプログラム（将来はGoも）を、作り直さずにそのまま動かすことを目指す。「Linuxのバイナリを走らせることは目標にしない」（2026-09-17）は、この決定で置き換える。
   - 合わせる相手は、これまでどおりLinuxのx86_64である（番号・引数・構造体の配置・errno・定数・レジスタ規約・シグナルのフレーム）。AArch64の表をLinuxのarm64から採ることも変わらない（`ADR-0070`）。
   - 最初に動かすのは、静的リンクしたプログラムである。動的リンクをいつ扱うかは、ここでは決めない（下の「決めないこと」）。
   - 「完全互換」は目指す先であり、一度に全部を入れるという意味ではない。入れる順は、動かしたいプログラムが実際に使うものからにする。最初の相手はSeinasである。
2. **順序をGUI優先に変える。** 次の順に進める。
   1. SeinasをZeikOSの上で動かすための、最低限の実装
   2. Seinasを組み上げる（Smithay経由。Wayland）
   3. ZeikOSの上でSeinasの動作を確かめる
   4. ARMの浅い仮対応（`ADR-0070`）
   5. スレッド
   6. 2 CPU以上
   7. 実機対応
   - `ADR-0069`の「段と順序」の7番から12番は、この順で置き換える。済んだ段（1番から6番）は変わらない。
   - 「最低限の実装」の中身は、段ごとに設計を見せてから決める。棚卸しで挙がった候補は、`syscall`命令の入口、位置独立の静的リンクの実行ファイルを読むこと、TLS（`arch_prctl`）、シグナルの最小限、無名の`mmap`と`munmap`、`epoll`・`eventfd`・`timerfd`、ソケットの旗、画面と入力の装置の入口、マウスである。
3. **`int 0x80`の入口は残し、`syscall`命令の入口を足す。** いまのユーザープログラムと検査は`int 0x80`の上に在るので、入口を足す間も動き続ける。`int 0x80`は、要らなくなった時点で消す。消す時期は、その時点で決める。
   - `ADR-0069`の決定4の3（`int 0x80`は移行の後に閉じる）と、`ADR-0020`のAddendum 4（併存は移行の間だけ）は、「閉じる時期を先に決めない」形に改める。

## 以前の方針と、変えた理由

| 項目 | 以前 | これから | 変えた理由 |
|---|---|---|---|
| Linuxのプログラム | 形は合わせるが、走らせることは目標にしない。走らせるかは未決 | そのまま動かすことを目指す | Seinasを動かすには、Rustの標準ライブラリとSmithayが呼ぶものを受ける必要がある。ZeikOS専用の層を別に作るより、Linuxに合わせるほうが、作るものが1つで済み、ほかのプログラムにも効く |
| 順序 | Seinasは実機対応の後（最後） | Seinasを最初に動かす | 画面に動くものが出る段階を先に置く。実機対応やスレッドは、動かす相手が決まってからのほうが、要るものを測って決められる |
| 入口の命令 | `syscall`へ移した後に`int 0x80`を閉じる | 両方を持ち、`int 0x80`は要らなくなったら消す | いまの37のユーザープログラムと全検査が`int 0x80`を前提にしている。閉じる時期を先に決めると、移す作業が入口を足す作業の前提になってしまう |

「ABIの形は合わせる」という考え方そのものは変わらない。変わるのは、その先に「だから、そのまま動く」を置いたことである。

## Alternatives Considered

- **Seinasの側にZeikOS専用の裏側を書く**: 採らない。Smithayと標準ライブラリの下の層（`rustix`・`calloop`・`wayland-rs`）がLinuxのシステムコールを直に呼ぶので、Seinasだけを書き分けても足りない。専用の対象（target）と標準ライブラリの移植が要り、作る量はLinuxに合わせる場合より多い（推測）。
- **順序を変えず、実機対応の後にSeinasを動かす**: 採らない。Seinasが実際に何を使うかを測らずに、スレッドや入口の設計を先に決めることになる。
- **`syscall`命令へ移した時点で`int 0x80`を閉じる**: 今は採らない。閉じるには、いまのユーザープログラムと検査を全部移す必要がある。入口を足す作業と分けたほうが、段を小さくできる。
- **互換の範囲を先に一覧で決める**: 採らない。使われない入口まで作ることになる。動かす相手が使うものを測り、そこから足す。

## 決めないこと

- 動的リンク（`PT_INTERP`と共有ライブラリ）をいつ扱うか。最初は静的リンクのプログラムだけを相手にする。
- `int 0x80`を消す時期。
- 自前のlibc（`ADR-0057`）と、いまのユーザープログラムを、Linux向けのlibcへ寄せるかどうか。
- 画面と入力の私物の入口（`ADR-0066`）を残すかどうか。
- AVXを使えるようにするかどうか（`ADR-0058`）。

どれも、その段の設計で案を出して決める。

## Consequences

- Linux向けに作ったプログラムを、ZeikOSのために書き直さずに試せるようになる。Seinasは、Linuxの上で作ったものをそのまま持ち込める。
- カーネルが受けるものが増える。入口・実行ファイルの読み方・メモリの配置・シグナルは、どれも人のレビューが要る変更である（`CLAUDE.md`の「人間レビューが必須の変更」）。段ごとに設計を見せてから入れる進め方は変わらない。
- いまの検査は、`int 0x80`・32 KiBまでの実行ファイル・4 KiBのユーザースタックを前提にしている。上限や配置を変える段では、起動ログやページの権限の参照が動く。入口を残すので、いまの検査は入口を足す間もそのまま使える。
- ARMの浅い仮対応・スレッド・2 CPU以上・実機対応は後ろへ動く。それぞれの決定（`ADR-0070`・`ADR-0069`）は変わらず、着手の順だけが変わる。
- 「Linuxと同じに見えるが、違う」所が残る間は、違いを持ち越しの行に書いて見えるようにしておく。
